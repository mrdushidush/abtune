## Catalog (HANDOFF §6, M1)

- 2026-10-02 · **Language scope: Hebrew and English first.** The catalog still takes the top tracks in every language by popularity, but only Hebrew gets a coverage quota, and only Hebrew and English get report sections and checks. French and Spanish quotas and checks are deferred · owner decision. This changes §6.2 stage 3 ("IL/FR/ES"), §6.8 and the §15 M1 criterion ("Hebrew/French").
- 2026-10-02 · **Popularity = ListenBrainz statistics dump + popularity API top-up.** The dump's per-user all-time top-1000 lists give a proxy (distinct users per song) that picks ~3.5M candidates. `POST /1/popularity/recording` (ListenBrainz + MLHD+) then gives exact listener counts for ranking, cached under `data/dumps/lb-popularity-api/` so rebuilds reuse the snapshot. `--no-api` builds from dumps alone · **brief discrepancy (§3.3):** the `datasets.listenbrainz.org` "popular recordings" and "per country" datasets are query endpoints, not bulk files, and returned a backend DB error on 2026-10-01.
- 2026-10-02 · Coverage quotas use artist country (MusicBrainz area, walked up "part of" links to a country) **or** lyrics/release language, not per-listener-country popularity · no bulk per-country popularity data exists (see above).
- 2026-10-02 · Downloads total ~72 GB (75.3 GB decimal, measured): the 60 GB pre-approval plus the 20 GB statistics dump · owner approved when choosing the popularity option. Downloading took 13 min at ~100 MB/s.
- 2026-10-02 · "Dev sample builds < 10 min" means **fetch-to-ready**: `abtune catalog fetch` installs the prebuilt 50k sample, and `abtune catalog sample` derives it from a full build, each in under 10 min. The multi-hour full build is measured and documented, not capped · owner decision. The sample is a GitHub release asset (public at v0.1).
- 2026-10-02 · The 5k fixture is committed at `data/catalog-fixture/` with its own CC BY-NC-SA 3.0 US license; code stays MIT · owner decision. See [DATA_LICENSES.md](DATA_LICENSES.md).
- 2026-10-02 · **Brief discrepancy:** `recording_first_release_date` is not in the MusicBrainz dumps (`admin/ExportAllTables` excludes it from replication). Years come from release events: track → medium → release → `release_country` / `release_unknown_country`, taking the minimum over every recording of the song.
- 2026-10-02 · Canonicalization has two levels. ListenBrainz canonical redirects collapse a recording into its canonical version (first album). Then songs are keyed by (first credited artist id, normalized title, version type): titles are lowercased, accent-stripped and punctuation-free, with remaster/live/feat./radio edit/single version/mono/stereo noise removed from brackets and dash suffixes. Remixes and acoustic versions keep their own titles · the brief's §6.2 rule. Keying on the artist id, not the credit string, means "A feat. B" and "A" credits of one song merge.
- 2026-10-02 · §6.6 version rule: one row per (artist, title); a different version type (live vs studio) survives only with ≥ 20 dump-proxy listeners and ≥ 20% of the top version's · this keeps iconic live takes and drops the long tail of concert recordings.
- 2026-10-02 · Language buckets: work (lyrics) language from the recording→work "performance" link first, then the canonical release's text language. `zxx` → `none` (instrumental), missing → `unknown`, `mul` → `lang_other`.
- 2026-10-02 · Genre clusters: tag votes × `data/tag_map.yaml` weights at three levels (recording, release group, first artist), each normalized and then blended 1 : 0.5 : 0.25. Weights < 0.1 are dropped, the top 4 kept. Tracks with no mapped tags fall back to the CC0 AcousticBrainz genre classifiers (`genre_source = ab`). Cross-level sums use DECIMAL, so parallel aggregation can't reorder them.
- 2026-10-02 · Non-music filter (§6.6), first match wins: placeholder artists (Various Artists, [unknown], …); length < 30 s; titles matching karaoke / "in the style of" / "originally performed by" / "tribute to"; release groups with an audiobook / spoken word / interview / audio drama / field recording secondary type; non-music tags (`non_music` in tag_map.yaml) outvoting genre tags at the most specific tagged level.
- 2026-10-02 · Scalar features: §6.3 formulas on mean classifier probabilities give `raw_*` values. The 8 non-mainstream scalars are then **quantile-scaled to (-1, 1) over the final catalog** (ties share their mean rank); `mainstream` = 2·popularity percentile − 1 · AcousticBrainz probabilities are bunched (danceability near 1, aggression near 0), so raw values would leave most of each axis empty while quiz answers target the whole axis. `raw_*` columns are kept for M3 tuning.
- 2026-10-02 · BPM half/double-time correction: < 70 BPM in edm/house/dance-pop/punk/metal/funk/kpop doubles; > 165 BPM in hip-hop/R&B/reggae/ambient/soundtrack/classical/folk/blues halves. Tempo axis 60 → −1, 180 → +1 before quantile scaling.
- 2026-10-02 · Intensity = 2·aggressive − 1 + ½·tag nudge + cluster prior (metal +0.4, punk +0.3). Complexity has no AcousticBrainz signal: ½·tag nudge mean + ½·cluster prior (jazz +0.6, classical +0.7, pop −0.3, punk −0.5, …), both in tag_map.yaml.
- 2026-10-02 · Imputation tiers: `ab_direct` (AB data on any recording of the song, including canonical redirects and merged MBIDs); `ab_sibling` (shares an ISRC, or performs the same work with the same first artist, so covers are excluded); `model` (ridge regression, below). Tier 4 (AI) is M7.
- 2026-10-02 · Tier 3 = per-dim ridge regression in TypeScript (ADR-0001: no Python). Features: 24 cluster weights, decade and language one-hots, standardized log listeners, and **leave-one-out artist and release-group means** shrunk toward the global mean (pseudo-count 2). λ ∈ {0.1, 1, 10, 100} picked on a 5% validation split. Measured on a 5% random holdout and a 5% **artist holdout** (artist/album means masked), the proxy for post-2022 artists that have no AcousticBrainz ground truth. Splits use md5 of MBIDs, so they're stable across runs.
- 2026-10-02 · `feature_confidence` = 0.75 + 0.25·(mean classifier certainty |2p−1|) for `ab_direct`; × 0.8 for `ab_sibling`; 0.6 for `model` with an artist mean, 0.45 without.
- 2026-10-02 · Selection: rank by (listeners, listens, MBID); top up each quota pool with its next-best songs that have at least one known listener, trimming the lowest-ranked non-pool songs so the total stays at the target. Default target 2,000,000.
- 2026-10-02 · **Hebrew pool seeding.** Songs normally come only from the statistics dump's per-user top-1000 lists, and those hold just 15k of the 149k canonical recordings by IL artists, so the first full build found 16,434 Hebrew-pool songs against a 30,000 minimum. Now every canonical recording by an artist from a pool country, or with a title in a pool's script (`Pool.script`, "Hebrew"), becomes a song even if no top list has it, and the popularity API (ListenBrainz + MLHD+) ranks it. Measured on the 2026.09 dumps: 139,881 seeded songs, 137 extra API calls; in a 1,000-MBID sample, 37% had at least one listener.
- 2026-10-02 · Language fallback: a title in Hebrew script means Hebrew when no work or release language is recorded. Only Hebrew gets this: Arabic and Cyrillic script each serve several languages. Yiddish titles with no recorded language are the known error, and they're rare.
- 2026-10-02 · **Two Hebrew quotas.** `he` (IL artist or Hebrew language, minimum 30,000) fills mostly with Israeli psytrance/EDM that has an international audience: in the 2026.09 build, 20,066 of its 30,000 songs weren't in Hebrew. A second quota `he_lang` (Hebrew language, minimum 18,000 = every Hebrew song with at least 2 known listeners) follows · owner decision. `--he-min` and `--he-lang-min` override them.
- 2026-10-02 · Catalog determinism: every "pick one" has a total order ending in an MBID; float sums go through DECIMAL; exports sort by track_id; the API snapshot is a build input. `manifest.digest` = sha256 over the rows' JSON. A test rebuilds the synthetic catalog and compares digests.
- 2026-10-02 · Catalog versions are named after the MusicBrainz dump month: the 2026-09-30 dump builds `catalog-2026.09` (the brief's `catalog-2026.10` was an example). `--version` overrides it.
- 2026-10-02 · `data/tag_map.yaml` was tuned from the first build's "Unmapped tags": AllMusic-style compounds (pop/rock, alternative/indie rock), spelling variants (singer/songwriter, jazz rock, psy-trance), and Israeli-scene genres (oriental rock and metal, Orthodox pop, melodic house and techno). Identity tags (hebrew, israeli, jewish, nationalities) stay unmapped. About 4k Hebrew-pool songs have no tags and no AcousticBrainz data at all, so they get no cluster.
- 2026-10-02 · Export performance: the 10 quantile and percentile windows run over a narrow numeric table, and cluster maps are built with an unordered `list()` plus a per-row `list_sort` instead of an ordered aggregate. Over the wide rows (lists, maps) the stage took 21 min; now it takes ~1.5 min, with a byte-identical digest.
- 2026-10-02 · Catalog output: `tracks.parquet` (zstd) + `manifest.json` + `LICENSE.md`. `clusters` is `MAP(VARCHAR, FLOAT)`, the logical §6.5 shape; M3 decides the in-memory layout.
- 2026-10-02 · Dev sample and fixture: strata = (primary cluster, decade), with at least one per stratum and the rest by largest remainder. Within each stratum, half the picks are top by popularity and half evenly spaced down the popularity ranking, so the `mainstream` range stays covered. A Hebrew floor comes first (1,000 in the dev sample, 100 in the fixture). Fixture ⊂ dev sample ⊂ catalog, with values copied, not recomputed.
- 2026-10-02 · No tar dependency: a small streaming tar reader/writer plus Node 24's built-in zstd. The bz2 MusicBrainz dumps go through the system tar (bsdtar on Windows, with lbzip2 on Linux when present) · bz2 has no fast pure-JS decoder, and bsdtar ships with Windows 10+.
- 2026-10-02 · Each dump's `COPYING` is checked on every build (CC0 for MB core, canonical and LB stats; CC BY-NC-SA 3.0 US for MB derived). A license change stops the build.

## Generator and eval (HANDOFF §9, §17, M3)

- 2026-10-02 · The generator's only input about the listener is a quantized **TasteVector**: per scalar a target (×100) and a confidence κ (×100), per group a distribution (×1000) or null for "no preference". Integers only · a share link (M6) carries this vector plus the seed and reproduces the exact playlist without the answers or the AI layer (§4.4, §9.5).
- 2026-10-02 · **Popularity lean** (owner decision): a virtual answer of weight β toward `mainstream` = m0 is folded in before κ, so thin evidence leans to well-known songs and any real mainstream answer (weight 1) outweighs it. Measured: 98–100% of random 10-question runs touch `mainstream`, so this is a weak prior, not a fallback.
- 2026-10-02 · `CatalogColumns` = typed arrays in track_id order: 9 scalars and confidence (Float32), top-4 cluster index/weight pairs, primary cluster, decade, language (Uint8 indices into the bank's dimensions), first-artist id and normalized-title id (Int32, dense ranks), year · the reader streams numeric columns out of DuckDB (`chunk.getColumns()`): 2M rows in ~8 s and ~230 MB. Converting the MAP/LIST columns to JS objects took 17 s and 3.6 GB.
- 2026-10-02 · The §9.3 "duplicate normalized titles" rule uses the catalog's own `norm_title` SQL macro (feat./remaster/live noise stripped), so the generator and the catalog dedupe agree on what one song is.
- 2026-10-02 · Scores are quantized to integers (2^20) before any sort or sample; sampling weights are integers (2^16 for the best candidate) drawn with `rng.int`. The only transcendental call is `Math.exp` in the softmax, which V8 implements itself (not the OS libm); a pinned digest over fixture playlists runs on Linux, Windows and macOS CI.
- 2026-10-02 · A group without evidence drops out of the §9.1 score (the other weights renormalize) and its cells use the catalog's natural shares. Language: instrumental and unknown-language tracks score a neutral L; one language at p ≥ 0.8 becomes a hard filter (§7.3).
- 2026-10-02 · Cells: empty cells are dropped before the 90% cut, so mass isn't wasted on (cluster, decade) pairs with no tracks. Slots are allocated by largest remainder in rounds: a cell that can't fill its share (artist caps, few tracks) is closed and the remainder re-split over the open cells, then over the cells past the cut. If that still falls short, the prefilter, then the language filter, is relaxed with a warning; only the whole catalog failing gives `catalog_exhausted`.
- 2026-10-02 · Unclustered tracks (8.8% of the catalog, 46% of Hebrew-language tracks) are eligible only when the listener has no genre preference · they have no G(t) evidence. Known gap; the catalog stays frozen for M3 (owner decision).
- 2026-10-02 · MMR similarity = 1 for the same artist, else 1 − mean |Δfeature| / 2 over the 9 scalars, against every track already picked. Temperature (0.1) and λ_mmr (0.15) stay at the brief's values and are not tuned · they trade relevance for variety, and a fit-only objective would drive variety to zero.
- 2026-10-02 · **Sequencing uses rank-matched energy targets**: positions are ranked by the §9.4 curve's height and take the playlist's energies of the same rank, then the greedy |energy − target| + 0.3·|Δtempo| placement and adjacency repair run. Quantile targets asked for more high-energy tracks than a playlist has: the peak came early and the last third was all low. Consequence: the opener sits around the 20th energy percentile, not the median; a median start is impossible when only the last 15% of the curve is below it.
- 2026-10-02 · Archetype era = decade-weighted mean year (decade midpoints) < 2000; no decade evidence → "Modern" · the catalog's mean year is ~2006. Title parts without evidence are left out.
- 2026-10-02 · **Personas**: the brief's 12, with "French chanson + French touch" replaced by "Israeli rock & pop in Hebrew" (owner decision). The persona bot scores each side: a scalar earns |mid| − |v − mid| (closer than neutral), a target category +v·weight, another category in a targeted group −½v. It picks the higher side; near-ties (< 0.05) give `both` if liked, else `skip`; if both sides score below −0.25 it skips · forced "least bad" picks taught a classical persona that it loves classic rock ("Bon Jovi or Britney?"), which a real listener would skip.
- 2026-10-02 · Persona fit per track = (share of cluster weight in target clusters) × decade weight × language weight × (share of scalar ranges met), averaged over the playlist · the brief's "share of tracks in target clusters × decades × scalar ranges", made continuous so the tuner sees small changes.
- 2026-10-02 · **Seed bank Hebrew path** (owner decision): `spanish_other` now unlocks on `hebrew_french=b` only; `einstein_omeradam` pri 60 → 85 and `mizrahi_israelirock` 64 → 82 · after "Hebrew", "Other languages" reads as "Hebrew too" but counted lang_other +1, which outweighed the Hebrew answer: the 50-question Hebrew persona got p(Hebrew) 0.22 and no Hebrew songs. After the fix: 0.97. Golden sequences unchanged. A core "Hebrew or English?" question (Hebrew within 10 questions) was declined for now: the first 10 stay market-neutral.

Objective = mean persona fit over modes 10/20/50/100, rejected unless fit rises strictly with depth and diversity stays ≥ 90% of the starting settings'. Final constants, starting from the brief's:

## Web UI (HANDOFF §4, M4)

- 2026-10-02 · **Look: dark neon A/B** (owner's pick): ink `#0b0b12`, option A pink `#ff5c8a`, option B cyan `#4cc9f0`, heavy system-font type, big emoji. Dark only. Single-series profile charts use violet `#9a6cf5`, checked with the dataviz palette validator against the card surface `#14141d` (the brand pink and cyan fail its dark lightness band).
- 2026-10-02 · **English UI, RTL-safe** (owner): every string lives in `apps/web/src/client/strings.ts`, and layout uses logical properties. Track titles and artists use `unicode-bidi: plaintext`, so a Hebrew title reads right to left, and they are aligned by the UI's direction (`text-left rtl:text-right`) because `start` would follow each title's own direction and scatter a mixed list. Live hints are structured data from the engine (`profileHints`), worded by the UI. A Hebrew UI is deferred.
- 2026-10-02 · **The server never sees answers.** The browser runs the quiz, computes the taste vector (plus tweaks) and the seed, and POSTs only `{taste, seed, length, engine_version, catalog_version}` to `/api/playlist`. Spicy answers stay on the device (§13) with no consent flow needed, and the request is exactly M6's share payload. A test asserts the body holds no question id, label or choice. Caveat: `tasteVector` calls `Math.exp`, which may differ in the last bit between JS engines; a quantized value changes only on an exact .5 boundary, and the playlist is a pure function of the vector that gets shared.
- 2026-10-02 · Version guard: `/api/health` reports `engine_version` (semver + bank hash). A request made with another engine or catalog version gets 409; the client refetches health, or asks for a reload when its own bundle is stale.
- 2026-10-02 · The server listens first and loads the catalog in the background (`catalog.status`: loading → ready | error; 503 with `Retry-After` meanwhile). Full catalog: 7.7 s. `POST /api/playlist`, 50 tracks, 100 random sessions: p50 257 ms, p95 522 ms, generation plus the DuckDB track lookup. Request bodies are capped at 16 KB and never logged.
- 2026-10-02 · **Tweaks are presets on the taste vector** (engine `applyTweaks`): more energy / calmer, happier / moodier, more hits / deeper cuts, newer / older; ±2 steps per axis; they persist through reshuffle and "10 more". The personality card and the archetype in the title use the untweaked profile; the description lists the tweaks. Per step: the axis's scalar target moves 0.5 (energy also moves tempo 0.2 and dance 0.15) and its κ goes to 1; every other scalar keeps 0.6 of its κ ("focus"); era moves 40% of each decade's mass one decade, or, without era evidence, applies an exponential ramp of 0.35 per decade · the first version (shift 0.3, κ ≥ 0.8, no focus) moved a dev-sample playlist's mean energy by only +0.07 per step, some personas the wrong way: one scalar is 1/9 of the scalar score. Measured on the full catalog (12 personas × 3 seeds, 20 answers, 50 tracks), one step moves mean energy +0.28 / −0.35, valence +0.40 / −0.39, mainstream +0.37 / −0.20 (scalars on the −1…1 scale), and the mean year +3.5 / −2.3 years at a 0.3 era shift (0.4 measured on the dev sample: +4.4 / −3.2). At two steps every persona moves the right way; `packages/cli/test/acceptance/tweak.test.ts` pins the direction on the fixture.
- 2026-10-02 · Live hints (§4.2) start after the 3-question hook. Era thresholds scale with the number of decades n: one decade at ≥ max(0.35, 2.8/n), or two adjacent ones at ≥ max(0.45, 3.6/n) · τ_decades = 1 keeps decade shares soft, and with fixed 0.5 / 0.6 thresholds no era hint appeared in 20-question runs. The chip shows a hint that became true within the last 2 answers, else the current hints take turns every 2 answers, so it doesn't sit on one hint for 15 cards.
- 2026-10-02 · **Export** is `@abtune/connectors`, pure and dependency-free, so the browser builds the file and downloads it as a Blob (M8's MCP will reuse it). M3U is written as `.m3u8` (UTF-8): `#EXTINF:<s>,<artist> - <title>` plus the MusicBrainz recording URL as each entry's location, since there is no local file. CSV: RFC 4180 with CRLF, UTF-8 **without** a BOM (transfer tools are the target, and a BOM corrupts the first header for some parsers), header `Title,Artist,Album,Year,ISRC,MusicBrainz ID` with the first ISRC; a cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading apostrophe against spreadsheet formula injection, since titles are community data. ## Hit-first playlists, Israeli market, quiz variety (owner decisions D1–D10, 2026-10-03)

- 2026-10-03 · **Why:** the owner tried M4. The quiz was fun, but almost every playlist song was obscure ("if we can't get a playlist where most songs are recognizable, users won't use the app"). - 2026-10-03 · **Hit signal (D2):** an international song's rank within its artist is the mean of its within-artist percentile by **proxy listeners** (ListenBrainz users with the song in their all-time top 1000; already used to pick candidates) and by **Various-Artists compilations** that carry it. On a 74-hit test set this puts the real hit in the artist's top 3 95% of the time; the API listeners managed 77%. The hit key within a decade is ln(1 + proxy listeners) + 0.5 · ln(1 + VA compilations). VA = artist `89ad4ac3-…`, compilation release groups, official/promo/no status. ## Genre stability and question variety (owner feedback after the hit-first build, 2026-10-03)

- 2026-10-03 · **Why:** the owner's 50-question playlist was Classic Rock 10% / House & Techno 90%. Ten more answers inverted it, and the 60-question playlist was the first one they liked. They also found that "most questions are the same every time". Their answer log wasn't available (no browser access), so everything below was measured on simulated listeners: the 12 eval personas plus 5 mixed tastes (rock first with some house, rock ≈ house, pop + hip-hop, metal + classical, indie + synth/chill), 8 quiz seeds each, consistent and with 15% of answers flipped. Scratch tools, not committed.
- 2026-10-03 · **Cause 1, the split:** p = softmax(s / 0.25) over *summed* evidence. Genre evidence grows with every answer (E ≈ 3 at 10 answers, 20 at 50, 38 at 100), so the split sharpens without limit: a lead of 0.55 is 90/10 whatever the totals. At 50 answers the top genre averaged 90% of the mix, and a top-genre flip between 50 and 60 moved the mix by 65 points on average.
- 2026-10-03 · **Fix 1, relative temperature:** τ′ = max(0.25, 0.15 · s_top) (`TasteParams.relativeTau.genres`). Below s_top ≈ 1.7 (about the first 10–15 answers) nothing changes; deeper, the split depends on s / s_top, not on how many answers were given. Top-genre share at 50 answers 90% → 67%; a flip moves the mix by 38 points instead of 65. Persona eval: fit unchanged (0.196 → 0.380 → 0.501 → 0.514 vs 0.197 → 0.374 → 0.498 → 0.513), canon 7.43 → 8.56, signature 71% → 75%, worst persona at 50 questions 0.06 → 0.14. Proportional shares p ∝ s^γ (γ 2–4) and τ ∝ √E also kept mixes but cost 0.02–0.05 fit.
- 2026-10-03 · **Cause 2, the order:** even with consistent answers, the top genre was a persona's main genre in only 78% of runs at 50 answers and 71% at 100. A forced choice adds evidence to the side picked even when the listener likes neither: the 2000s metalhead picked Avicii over Mozart, the big drop over chill vibes, Dua Lipa over Adele and Eminem over Drake, and led with EDM at 50 answers. Only 73 of the 276 genre pairs had a card that splits them. Metal was split only against classic rock and country, and rock vs house by one card.
- 2026-10-03 · **Fix 2, genre duels:** `data/questions/duels.yaml`, 30 deep cards, each pitting two genres that often end up neck and neck at the top (rock/house, metal/EDM, chill/hip-hop, classical/techno, indie/folk, hip-hop/R&B, …). New `unlock_if.all_top_genres`: the card unlocks only when every listed genre is in the top 3. A first version that unlocked on either genre made things worse: two genres the listener doesn't love dueled, and one gained (Hebrew-mizrahi persona fit 0.14 → 0.03 at 50 answers). From position 21 on, a card scores × (1 + 3 · duel value), with duel value = c₁ · c₂ · min(|Δ₁|, |Δ₂|) for the best pair of genres it moves in opposite directions and c = max(0, s) / s_top (`DEFAULT_DUEL` 3, `DEFAULT_DUEL_FROM` 21). The bonus from position 4 raised fit at 20 answers but pushed the language card out of the first 20 (Hebrew-mizrahi persona 58% → 1% Hebrew at 20 questions) and cost canon hits (8.4 → 6.8).
- 2026-10-03 · **Measured with both fixes** (simulated listeners, seeded quizzes): the right top genre at 10/20/50/100 answers 50/60/78/71% → 49/71/87/82%; top-genre flips between 50 and 60 answers 13% → 2% (consistent) and 15% → 10% (15% flipped); mix change between 50 and 60 0.17 → 0.11. **Persona eval** (full catalog, 5 seeds, [report](eval/2026-10-03-duels.md)): fit 0.196 → 0.373 → 0.497 → 0.513 became **0.197 → 0.372 → 0.527 → 0.568** (margin +0.371), canon 7.60 → **8.34**, signature 71.7% → **73.6%**, Hebrew personas 64.1% → **64.5%** Hebrew, p95 224 ms, 0 violations. Biggest gains at 100 questions: 2000s metalhead 0.12 → 0.42, EDM festival 0.44 → 0.60, Indie folk 0.52 → 0.58. Still weak: Hebrew-mizrahi (0.19 at 100) and, with 15% of answers flipped, fit still dips from 50 to 100 (0.483 → 0.397).
- 2026-10-03 · **Repetition:** a retake of a 50-question quiz showed 65% of the same cards and 84% of the same questions (counting any variant). `data/questions/variants.yaml` adds 89 variants: two each for the 22 families asked in ≥ 75% of 50-question sessions, one each for the 45 asked in 40–75%. A variant copies its family's fx, pack and pri exactly (generated from the canonical question, so it can't drift); only the words, artists or songs change. Retake: **14%** identical cards. The share of the same *questions* stays at 84%: the information-gain ranking reaches the same families over 50 cards, and widening the draw costs fit (measured earlier the same day). Three families asked in 40–75% still have no variants (btc_xrp, vinyl_streaming, plan_spontaneous). The new cards (variants and duels) await the owner's review.

## Spotify connector (HANDOFF §11.1, M5)

- 2026-10-03 · **Checked against Spotify's docs** (§0.3). The February 2026 dev-mode changes match §3.1: `POST /me/playlists`, `POST /playlists/{id}/items` (at most 100 per call), search `limit` ≤ 10. `external_ids` (ISRC) was removed in February and restored in the March 2026 changelog. Developer Terms IV.3.1–3.2 forbid databases of Spotify Content and allow only temporary caching of metadata, so no ISRC→URI table is kept (see the match cache below).
- 2026-10-03 · **Sign-in on the server, not in the browser.** Authorization Code + PKCE (no client secret, so a self-hoster only pastes a Client ID). The server keeps the refresh token in `data/spotify/tokens.json`: AES-256-GCM per entry, with a key derived (HKDF) from `TOKEN_ENCRYPTION_KEY` and the entry key as AAD. An HttpOnly, SameSite=Lax cookie holds a random connection id, and the file is keyed by its SHA-256, so the file has neither tokens nor cookie values in the clear · §12 wants `push_to_spotify` to use "a completed OAuth in the web app", and a browser-only flow would keep the token where the MCP server can't reach it. The browser never sees a Spotify token. Scopes: `playlist-modify-private playlist-modify-public` only.
- 2026-10-03 · Sign-in starts on the redirect URI's host: opened at `localhost:8787`, Connect first moves to `127.0.0.1:8787`, because cookies are per host and Spotify accepts only the loopback IP. A page open at another address than the redirect URI's offers a link to the same playlist there (its share link). `state` is checked against a short-lived cookie (login CSRF); a POST whose `Origin` isn't the server's own is refused. The sign-in returns to the page it left (`?spotify=connected|denied|not_allowed|expired|error`), the app removes the parameter and reopens the Spotify sheet. A 403 on `/me` right after sign-in (an account not on the app's User Management list) is reported as such.
- 2026-10-03 · **Matching:** each ISRC (up to 3 per song) as `isrc:<code>`, `limit=1`, `market=from_token`; an ISRC hit is trusted. Then `track:"<title>" artist:"<first credited artist>"` (`limit=10`), and the same words without field filters if that found nothing. A text result needs title similarity ≥ 0.85 (Levenshtein ratio after the catalog's own version-noise stripping: remasters, "feat.", radio edits), the **same numbers** in both titles, and an artist match on any credited name (≥ 0.85, numbers equal too). A live version is rejected unless the catalog song is live · without the numbers rule, "Song 9" matched "Song 90" in the tests, and "Symphony No. 5" scores 0.92 against "No. 9". Two catalog songs that are the same Spotify track count as one; the second needs a replacement.
- 2026-10-03 · **Backfill keeps N songs** (§11.1.3). For each song Spotify doesn't have, the generator picks one song from the same (primary cluster, decade) cell (new engine option `sameCellAs`), by an artist not on the list, from the first playlist's taste, seeded by `followUpSeed(seed, "backfill", n)`. If that cell has nothing left, any cell. Up to 3 rounds; the replacement takes the missing song's place. The same push gives the same replacements. Engine semver unchanged: existing inputs give the same outputs.
- 2026-10-03 · **Push order:** match everything (3 searches in flight), backfill, and only then create the playlist and add the songs in batches of 100. A quota or allowlist error during matching leaves no empty playlist behind; a failure while adding reports the half-filled playlist's link. Private by default; the description ends "Made with ABTune" (the brief's "Made with Either FM"), cut to Spotify's 300 characters, without angle brackets.
- 2026-10-03 · **Errors** (§11.1): 401 → refresh and retry once (a refresh that gets `invalid_grant` forgets the connection, and the UI offers Connect again); 403 → the allowlist / Premium message, with Spotify's own text; 429 → wait out `Retry-After` up to 30 s, pausing every request of that push, at most 3 times, then `rate_limited` with the wait; 429 with `reason: QUOTA_EXCEEDED` (at the top level or inside `error`) → stop at once and offer CSV export; 5xx → one retry after 1 s. One push at a time per browser (409 `busy`).
- 2026-10-03 · **Match cache:** in memory, per server process, per Spotify user (market), misses included, 1 hour, 5,000 entries. Pushing an edited playlist again doesn't search for the songs already matched. Nothing about Spotify tracks is written to disk.

## AI layer (HANDOFF §10, M7)

- 2026-10-03 · **Owner decisions:**
  - The server calls the model; the browser never talks to it.
  - **Local models only** in v0.1: `openai_compat` (LM Studio, Ollama, llama.cpp server, vLLM), `none`, and a test mock.
  - Rerank (T2) has its own switch, off by default.
  - OpenRouter, Jev (§3.2, §10.3) and Anthropic are not built. `AI_PROVIDER=openrouter|anthropic` turns the AI layer off with a clear message, and `OPENROUTER_API_KEY` / `JEV_*` are gone from `.env.example`.
  - AI is off by default (`AI_PROVIDER=none`), and a listener turns it on per quiz ("AI touches" on the setup screen, offered only when the server has a model).
- 2026-10-03 · **`@abtune/ai`:**
  - **Provider:** chat completions with `temperature 0`, `seed 42`, `response_format: json_schema` (strict, with enums from the bank's dimensions, so a constrained decoder can't invent keys), and an optional `reasoning_effort` (`AI_REASONING_EFFORT=none` for Qwen 3 in LM Studio).
  - **Size cap:** responses over 64 KB are read no further and count as `oversized`.
  - **Prompts** are versioned files in `packages/ai/prompts/*.md` (front matter `version:`, a system part, a `=== user ===` template). The rendered prompts and schemas are pinned as golden files (`packages/ai/test/golden/`).
- 2026-10-03 · **Guardrails (§10.4):**
  - Parse the JSON (a ```json fence is tolerated), validate the shape with zod, then clamp. An unknown key is dropped, and 0.9 becomes 0.3, so a nearly right answer still counts.
  - An invalid answer is retried **once, with a note appended**: a deterministic server would repeat the same answer word for word.
  - A timeout, a dead server or an oversized answer falls back at once, with no retry.
  - **Cache:** every answer is cached by `sha256(provider, base URL, model, task, prompt version, messages, schema)`, in memory only (LRU, 500 entries). Nothing derived from answers is written to disk (§13). Identical requests in flight share one call.
  - **Logging:** failures are logged by kind only (`AI interpret: timeout`), never a prompt or an answer.
  - **Time limit:** 20 s per call (`AI_TIMEOUT_MS`); rerank gets 20 s per 25 songs.
- 2026-10-03 · **T1 Interpret and T3 Tweak return a bounded adjustment, not a profile** (`engine/src/adjust.ts`). `TasteAdjust` holds integer maps ×100: scalar deltas within ±0.3, genre and decade boosts within ±0.5 (§10.2). Languages are never adjusted. How `applyAdjust` works:
  - **Scalars:** the target moves by the delta, and κ rises to at least 0.40 (`AI_MIN_WEIGHT`, about two answers at K = 5), so an AI-only dim counts.
  - **Groups:** a boost b multiplies a share by 1 + 3b, or divides it by 1 − 3b (±0.5 = ×2.5 or ÷2.5). A boosted category starts from at least 2%. A group with no preference starts from uniform.
  - **Plain arithmetic, no `Math.exp`:** every JS engine gives the same integers.
  - The result is again a `TasteVector`: like preset tweaks, its outcome is what gets shared.
- 2026-10-03 · **Which taste is which:**
  - **Card taste:** T1's adjustment is baked into it, so the personality card shows the AI-informed profile.
  - **Playlist base:** the card taste with the free-text tweak (T3) applied (`playlistBase`). The preset tweaks, "+25 deeper cuts" and swaps stack on it exactly as before.
  - **Titles:** T3's title over T1's over the engine's, cleaned (no control characters, one line, ≤ 60 characters). The blurb is ≤ 160 characters.
  - **Inputs:** T1 sees the answered pairs as text ("chose "Bon Jovi" over "Britney Spears"", with the card's question when it has one), the engine's profile in words with dimension keys, and the keys it may use. T3 sees the profile and the request (≤ 200 characters).
- 2026-10-03 · **T2 Rerank chooses; it never invents** (`engine/src/generate/rerank.ts`):
  - **Shortlist:** the generator makes a shortlist of min(150, 3N) songs from the same taste and seed. The model sees it numbered (`n. Title — Artist (year, genre)`, catalog text only) and returns `{picks: [{n, why}]}`.
  - **Choosing:** `chooseFromShortlist` gives each (genre, decade) cell its share of N (largest remainder), takes the model's picks in order within each share, then fills by score, keeping §9.3. `playShortlist` sequences them (§9.4).
  - **Bad answers:** numbers outside the list, repeats, fractions and made-up ids are dropped. Nothing valid → invalid → retry → the classic playlist with a notice.
  - **Replay:** the chosen positions (`picks`, ascending) go back to the client and into share links. `POST /api/playlist {picks}` replays them without the model. §9.3 is checked again, because positions from a link are untrusted.
  - **Scope:** rerank applies to the first page only; "+25 deeper cuts" and swaps stay classic. "Why" notes are shown on the rows (≤ 80 characters) and aren't shared.
- 2026-10-03 · **Privacy (§13, §16 #9):**
  - **Filtered twice:** `answersForAi` (engine) drops skips and `sensitive` questions in the browser, and the server filters again by its own bank. A sensitive answer reaches the model only with the session's opt-in **and** `ALLOW_SENSITIVE_TO_AI=true`. The opt-in is offered on the setup screen only then, with the spicy pack on, is never remembered, and says where the data goes.
  - **Share links:** a title or blurb made from sensitive answers never goes in one.
  - **Playlist requests:** they still carry a profile only. Rerank sees the profile and catalog text, never answers.
  - **Tests:** a mock model that records every payload, a spy on `console.*`, and share codes, each with the opt-in off, on the client only, and on both (the positive control).
- 2026-10-03 · **Share format 2:** format byte 2, then format 1's fields, a flags byte, and optional fields:
  - the T3 adjustment, as sparse (index, zigzag value) pairs
  - rerank picks, delta-encoded
  - the AI title and blurb in UTF-8 (a hand-written codec that rejects overlong and malformed sequences; the engine still uses no text APIs)
  
  A share without AI fields is still format 1, byte for byte. A 25-song AI playlist with a tweak, picks and a title was a 337-character link. The MCP server reads format 2 (adjustment, picks, AI title) and drops the picks, with a note, when a length, reshuffle or tweak override reshapes the shortlist.
- 2026-10-03 · **API:**
  - `POST /api/ai/interpret {engine_version, answers, taste, include_sensitive?}` and `POST /api/ai/tweak {engine_version, text, taste}` return `{adjust, title, blurb, sent?}`, or `503 ai_off` / `502 ai_failed {reason}`.

## Security hardening (owner, 2026-10-03, before M9)

A read-only review of the server, Spotify, AI, MCP, catalog fetch, client, Docker, CI and dependencies (`pnpm audit`: no known vulnerabilities), then fixes for everything it found. The owner chose the scope: all six findings, no per-IP rate limiting.

- 2026-10-03 · **Open redirect (fixed):** `safeReturn` let `/.//evil.example` and `/%2e//evil.example` through, and `withOutcome`'s URL round trip turned them into `//evil.example`, which a browser follows off-site. `/api/spotify/login?return=…` sent a 302 there (after the real Spotify consent, when Spotify is set up). Both now take only the parsed path, query and hash on a sentinel origin, with leading slashes collapsed.
- 2026-10-03 · **Catalog fetch path traversal on Windows (fixed):** archive names were split on `/` only, but Windows also reads `\` (and `C:`) as path syntax, so `..\victim/manifest.json` escaped the staging folder and the install step's recursive `rm` then deleted the escaped-to folder (reproduced). Each part of an archive path, and each manifest file name, must now match `^[A-Za-z0-9_-][A-Za-z0-9._-]*$`. The `.sha256` check proves integrity only: it comes from the same place as the archive.
- 2026-10-03 · **MCP `export_playlist` (fixed):** it wrote and overwrote any path. The host's model picks the path, and a share link's title and blurb (up to 220 characters anyone can write) reach that model. Now a file must stay inside the export folder (`EXPORT_DIR`, default the working directory; checked on the resolved path and again after symlinks), must have its format's extension (`.m3u8`/`.m3u`, `.csv`, `.xspf`, `.json`), is never a symlink, and replaces an existing file only with `overwrite: true`.
- 2026-10-03 · **Security headers (added):** Hono `secureHeaders` with a strict CSP (`default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `img-src 'self' data: blob:`, `connect-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `nosniff`, COOP/CORP same-origin. The built SPA has no inline script or style (React's `style` props are CSSOM, which CSP allows). **`Referrer-Policy: same-origin`, not `no-referrer`:** under no-referrer browsers send `Origin: null` on same-origin POSTs, which the cross-site check refuses. No HSTS: HTTPS is the proxy's business. Checked in headless Chrome against the full catalog: setup, a 20-card quiz, the result and the share card (a `blob:` image) render with no CSP violation, and the app's own POSTs pass the Origin check.
- 2026-10-03 · **Host allowlist (added) against DNS rebinding:** a page that points its own name at 127.0.0.1 passed the Origin check (Origin and Host were both its name). It couldn't reach Spotify (the cookie belongs to 127.0.0.1), but it could drive the AI routes and the local GPU. The server now answers only to `localhost`/`*.localhost`, IP literals (rebinding needs a name) and the host names in `APP_BASE_URL` and `SPOTIFY_REDIRECT_URI`; anything else is 403 `unknown_host`.
- 2026-10-03 · **AI limits (added):** `AiGate` in the runtime lets 1 model call run and 4 wait; more fail as `busy` (a new `AiFailureCode`, with its notice), and a caller that leaves while waiting gives up its place. The time limit starts when the call runs. Rerank now gets the request's abort signal, so a client that leaves stops its GPU work (it ran to the time limit before).
- 2026-10-03 · **Checked, no change:** PKCE S256 + state bound to an HttpOnly cookie; tokens AES-256-GCM with the entry key as AAD; cookies HttpOnly, SameSite=Lax, Secure on https; minimal scopes; Origin checks on the cookie-bearing POSTs; strict input validation and body limits on every route; AI output schema-checked and clamped to known keys; sensitive answers filtered again on the server; no `innerHTML` in the client; static serving resists encoded `..` and `\`; no shell in subprocesses; Docker runs as `node` on 127.0.0.1; no secrets in git; CI `contents: read`. **Before the repo goes public (M9):** pin the CI actions to commit SHAs.

## Capacity (2026-10-08)

- 2026-10-08 · **Measured on abtune.com** (Hostinger KVM 1, full catalog, AI off; the owner ran a closed-loop test of 300 random 20-answer sessions, 50 tracks each, 15 s per level):
  - `POST /api/playlist` levels off at **2.2–2.3 playlists/s** (about 0.44 s each); p50 0.51 s with 1 client in flight, 0.90 s with 2, 1.8 s with 4 and 3.2 s with 8. No errors.
  - Generation is synchronous on one event loop, so requests queue one behind another, and page loads wait with them.
  - At about 1.5 playlists per visitor and a 4-minute visit: about 180 visitors on the site at once at half load, and 360 at the ceiling.
  - Locally, pinning the server to one core with Windows affinity gave a false collapse (0.3/s at 8 clients): DuckDB still saw 12 cores and started 12 threads. With DuckDB at 1 thread it held 1.1/s on a desktop core.
- 2026-10-08 · **Playlists per visitor (owner: "add a rate limit to /api/playlist"):** replaces "no rate limit for the beta". Per-IP limits don't stop a spread-out flood; that is the Cloudflare tunnel's job.
  - **The limit:** a token bucket per visitor, `PLAYLISTS_PER_MINUTE` tokens refilled evenly over a minute, so a visitor may use a whole minute's worth at once. The public kit sets 20: a visitor in a loop gets at most about 15% of the measured capacity, while a person tweaking and swapping quickly rarely reaches 20 in a minute.
  - **Who a visitor is:** the address the trusted proxy (Caddy or cloudflared) puts last in `X-Forwarded-For` (`TRUST_PROXY`; earlier entries come from the client and are ignored), else the socket's address. An IPv6 address counts by its /64.
  - **Off by default:** a loopback install has one listener, and the tests and the eval post many playlists from one address. The public compose file sets the limit and `TRUST_PROXY`, so the server's `.env` needs no change.
  - **Past the limit:** 429 `rate_limited` with `retry_after` and `Retry-After` in whole seconds. The result and shared screens show "Lots of playlists in a row…" and ask again after that wait. "10 more" and swaps say "Too many changes in a row" and keep the playlist.
  - **Known gap:** a shared link replays its edits one request each. A link with more than about 19 edits opened by a visitor who has no tokens left loses the edits past the limit, counted in the "couldn't be found or replaced" note.
  - Idle buckets are dropped after a minute (they're full again by then), so memory stays bounded and nothing is written to disk.

## Playlist fit study (2026-10-08)

- 2026-10-08 · **The ask (owner):** "run the app using headless chrome 200 times… check if all the playlists generated are good enough. We must fine tune this — this is the main issue i got from the first few users."
- 2026-10-08 · **How it was measured:**
  - 200 seeded listeners (40% with the Israeli pack on, as an Israeli visitor gets it), each with a taste in genres, decades and language, played the real app in headless Chrome against the full catalog at 10, 20, 50 and 100 cards, answering each card by their taste.
  - Each playlist was judged by rule. A song fits when it is in a genre the listener likes, within a decade of an era they like, and in their language. **Good**: at least 70% of the songs fit, and for listeners who want hits, at least 60% are recognizable. **Meh**: at least 50% fit. **Bad**: fewer.
  - The same listeners gave the same answers before and after. Changes were tried first on recorded quizzes (replayed without the browser) and simulated listeners, then checked in the browser.
- 2026-10-08 · **What went wrong, by cause:**
  - **Eras:** with decades at τ = 1, a 10-card profile was nearly flat across decades, so a 2010s fan's playlist pulled in 1950s–70s classics (Paul Anka, "Dancing Queen", "Unchained Melody").
  - **Ties between genres:** a forced choice raises whichever side wins, so a genre the listener doesn't care about can tie the one they love. Duel cards settle that, but they started at card 21, so 10- and 20-card quizzes never got one. A hip-hop fan who picked pop artists over rock ones got an all-pop playlist.
  - **Language:** "Hebrew songs in your mix?" competed with every other card, and in a 10-card quiz it often came late or never, while language decides most of an Israeli playlist.
- 2026-10-08 · **What changed (engine 0.6.0):**
  - **Decades:** τ 0.3, with a relative τ of 0.1 · s_top so long quizzes keep the old split, and 0.3 × neighbor smoothing before the softmax (liking the 80s lifts the late 70s and early 90s). HANDOFF §7.3 amended.
  - **Duels from card 6** (was 21), and a genre is a contender only once its score is at least 1: picking Britney over Bon Jovi raises pop and dance-pop by 0.8 each, and with duels that early their tie took a mizrahi fan's 10-card profile to 94% dance-pop. HANDOFF §8.3 amended.
  - **21 new duel cards** (30 → 51) for the pairs the runs showed unsettled: rap against pop choruses, dance-pop and reggaeton; club tracks against pop ballads and pop songs; indie bands against pop stars; K-pop against western dance-pop; rock against country, jazz, soul, funk and movie scores; country against pop, folk, jazz and mizrahi; and more. Every duel card has `weight: 1.5`. The bank grows from 336 to 357 questions. The owner reviewed the new cards and kept all 21; two got a question line ("Who's on stage?", "Who's playing?") so they don't read "A guitar band or A pop star?".
  - **Lead slots:** a pack may declare `lead` positions. The Israeli pack asks "Hebrew songs in your mix?" second, and after "Lots of Hebrew", "Shlomo Artzi or Eyal Golan?" (Israeli rock or mizrahi) third.
  - **Lint:** a variant must have its canonical card's `weight`, so a variant can't change what an answer weighs.
- 2026-10-08 · **Results, 200 browser runs** (engine 0.5.0 live → 0.6.0):

  | | 0.5.0 | 0.6.0 |
  |---|---:|---:|
  | good / meh / bad | 84 / 32 / 84 | **127 / 17 / 56** |
  | songs in the listener's genres | 69% | 78% |
  | songs in a liked era (±1 decade) | 84% | 96% |
  | songs 3+ decades off | 9% | 2% |
  | recognizable (hits view, a top-3 song or a canon hit) | 97% | 95% |
  | page or API errors | 0 | 0 |

  - By quiz length, good (bad): 10 cards 15 (30) → 27 (25); 20 cards 32 (44) → 62 (23); 50 cards 27 (7) → 27 (5); 100 cards 10 → 11.
  - Israeli listeners 27 → 45 good (34 → 26 bad); others 57 → 82 (50 → 30). Hip-hop fans 17 good / 12 bad → 24 / 5; country 2 / 5 → 5 / 3; metal 4 / 10 → 9 / 5.
  - Still weak: a mizrahi fan who also likes English house gets a Hebrew and dance-pop mix (better, not good), and a hip-hop fan whose 20 cards never reach the hip-hop/pop duel still gets pop.
- 2026-10-08 · **Persona eval** ([docs/eval/2026-10-08-playlist-fit.md](eval/2026-10-08-playlist-fit.md)): mean fit at 10/20/50/100 cards 0.214 / 0.398 / 0.607 / 0.568 → **0.308 / 0.566 / 0.652 / 0.620**. §16 #3–#5 pass: p95 89 ms, 0 of 1,240 playlists break §9.3, and the 100-against-10-card margin is +0.311 (minimum 0.300). Across all modes, fit2 rises for 10 of 12 personas (Hebrew-mizrahi 0.231 → 0.324, jazz & soul 0.456 → 0.653, workout 0.383 → 0.514); 80s pop (0.526 → 0.483) and Israeli rock & pop (0.652 → 0.609) dip.

  - **Canon hits per 100 tracks fall from 9.45 to 5.13, under the recorded floor of 7.0** (D1); seed noise alone moves this figure by about 0.4 (the same code gave 5.55 before two cards got new question text, which changes the seeds). Signature songs (a famous artist's top 3) hold at 74% against a floor of 65%. An eval with the 30 old duel cards (unweighted) on engine 0.6.0 gave 5.95, so the decades change accounts for about 3.5 of the 4.3 drop: the canon list spans every era, and playlists that keep to the listener's eras find fewer of its hits (mainstream 25.5 → 15.9, jazz & soul 10.5 → 4.4, workout 17.5 → 8.9, EDM 7.1 → 4.4 from that alone). The new duels take EDM to 1.1 and workout to 5.3 while raising their fit2 (0.688 → 0.711, 0.416 → 0.514). An EDM fan now gets few of the big crossover hits (Titanium, Levels, Lean On), which may sit in dance-pop rather than EDM. Choices: investigate, or record a new floor.
  - **The Israeli rock & pop persona dips at 10 and 20 cards** (fit 0.25 / 0.37 → 0.16 / 0.27; better from 50 on), and its playlists are 62% Hebrew, down from 71%.
- 2026-10-08 · **Measured and rejected** (don't retry without a new idea):
  - A softer genre split (relative τ 0.3 or 0.5): worse.
  - Counting "A beat B" as evidence against B: didn't help.
  - Lifting songs whose year fits the era within each genre and decade cell: didn't help.
  - A relative τ of 0.5 for languages: the Hebrew personas fell from 79% to 30% Hebrew.
  - A relative τ of 0.3 for decades: long quizzes spread across too many decades.
  - `weight: 1.5` on the nine core genre-against-genre cards: a small gain in simulation, but "Classical or EDM?" became everyone's first card and lesser-evil answers took over; the metalhead and mizrahi personas collapsed.
  - Masking junk titles (medleys and the like): only about 7 in 6,425 songs.

## Counter integrity (owner, 2026-10-10)

- 2026-10-10 · **Why:** `/api/stats` is public, and the owner is about to use it to measure where visitors come from (source tags come next). Until now `POST /api/event` had no rate limit and counted any request without an `Origin` header, so one `curl` added a finished quiz.
- 2026-10-10 · **The check:** an event counts only when the request says it comes from this site's pages: an `Origin` header naming this host, or, with no `Origin`, `Sec-Fetch-Site: same-origin`. Pages can set neither header. A foreign `Origin` is refused whatever `Sec-Fetch-Site` says. The other POSTs keep the looser check, which lets a request without `Origin` through.
- 2026-10-10 · **The limit:** `EVENTS_PER_MINUTE`, the same token bucket and visitor key as the playlist limit (`TRUST_PROXY`, IPv6 by its /64), held in memory for a minute and never written down. Off by default; the public kit sets 30. A quiz sends a handful of events (started, finished, then any shares, exports and "10 more"), so a person stays far below it. Past it, 429 `rate_limited`, which `sendBeacon` ignores.
- 2026-10-10 · **Checked in headless Chrome 155** against a local server: an event sent from the app's page with `sendBeacon` and one sent with `fetch(…, { keepalive: true })` were both counted; the same POST from a script with no `Origin` got 403; 40 more from one address, after 4 earlier ones, gave 26 counted and 14 refused. Firefox and Safari weren't checked here. The Fetch standard has browsers send `Origin` on every POST, and the `Sec-Fetch-Site` fallback covers a browser that leaves it out of a beacon.
- 2026-10-10 · **What it doesn't stop:** a script that sets the headers itself still gets 30 events a minute per address (43,200 a day), and more addresses multiply that. Forging now takes intent and time, but it is still possible. A server-side count of playlists built (planned with the hourly funnel counters) gives a cross-check a script can't pass without building playlists, which are limited to 20 a minute per visitor and cost about 0.44 s of CPU each.

## Source tags (owner, 2026-10-10)

- 2026-10-10 · **Why:** the owner wants to know which of ABTune's own accounts (X, Instagram, TikTok) bring people who finish a quiz, with counts only: no IDs, cookies or IP addresses, so the privacy promise holds.
- 2026-10-10 · **The tag:** a link may carry `?via=x`, `ig` or `tt` (`VIA_TAGS`); any other value is ignored, so nobody can make up counter names. The browser keeps the last tag in local storage for 7 days from the link that set it (`abtune.via`); a newer tagged link replaces it. The address bar keeps `via`, so "Open in browser" from an app's own browser carries it along.
- 2026-10-10 · **The counts, per tag:** `via_<tag>_open`, a day this device opened the site with the tag (once per UTC day); `quiz_start_via_<tag>`; and `quiz_done_via_<tag>`, once per quiz like `quiz_done`. So per tag, on honest traffic, finished ≤ started ≤ opens, except for quizzes that cross midnight UTC. The day's open is counted again (still once a day) when a quiz starts or finishes, so a page opened before midnight doesn't leave a quiz after it without its day's open.
- 2026-10-10 · **A quiz counts for the tag it started with.** The first build credited the tag at the finish. In headless Chrome, a visitor who finished a quiz from an X link and later opened an Instagram link saw the saved result again, and it counted as an Instagram finish with no Instagram start. Now the start stores the quiz's seed and tag (`abtune.via.quiz`), and the finish credits that tag, only when its `quiz_done` is first counted. A quiz started with no tag stays untagged even if a tagged link opens mid-quiz. Without storage, a finish isn't credited to any tag: an undercount, never a double.
- 2026-10-10 · **Checked in headless Chrome 155** against a local server and the 50k catalog: landing on `/?via=x` counted one open; starting and finishing a 20-card quiz counted `quiz_start_via_x` and `quiz_done_via_x`, and the address bar still read `/?via=x` at the result; reloading and opening `/` added nothing; `/?via=ig` added only `via_ig_open`; `/?via=facebook` added nothing.
- 2026-10-10 · **Not counted on purpose:** someone who sees a post and later types the address has no tag. Site-wide totals stay next to the tagged ones, so the gap is visible.
